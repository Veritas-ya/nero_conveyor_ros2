# 仿真提前视觉与场景准备

`tools/probe_measured_network_scene.py --early-vision` 启用 MuJoCo 实验配置：顶视 RGB-D 相机位于仿真世界坐标 `[-0.50, 0, 1.65] m`，视觉检测世界 X 范围 `[-1.40, 0.70] m`。两项位于 `nero7_config.yaml`，是合成相机和仿真配置，不是实机标定。相机仍只由同一个渲染源提供 RGB 和深度。检测范围在进入 Nero7 前转换到机器人基坐标；抓取规划仍使用原来的抓取区间（本场景世界 X `[-0.20, 0.28] m`），不因检测范围扩大而扩大。

首次通过身份及几何检查的视觉帧可以在速度尚未合格时启动 OBB/网络抓姿计算和同帧场景准备。它仅供几何准备：速度记录为空，不构造测速结果；规划和轨迹创建仍须等待同一目标、同一代际的 Nero7 XY 卡尔曼测速合格和最新可用观测。抓姿与场景保留原始帧、时间、目标身份及摘要，不能跨目标复用；常规运行仍需在线场景复核。冻结视觉和关闭场景复核仅是显式开启的仿真对照，不能用于实机。

示例（使用本机已安装 MuJoCo 等依赖的 Python，带桌面显示）：

```bash
cd /home/ubuntu22/nero_conveyor_ros2
PYTHONPATH=src/nero_core:src/nero_bringup MUJOCO_GL=egl OPENBLAS_NUM_THREADS=1 \
  python tools/probe_measured_network_scene.py \
  --output runs/visualization/obb_early_vision_viewer.json \
  --early-vision --grasp-source obb --execute-sim --freeze-visual \
  --compute-budget-s 2.7 --seconds 30 --viewer --hold-viewer
```

将 `python` 换成已安装依赖的解释器。`--grasp-source obb` 不调用 GraspGen-X；该命令采用冻结视觉的仿真对照，而不是完整闭环。时间字段中的 `*_sim_s` 是仿真时钟，`*_wall_s` 是主机实际耗时；场景准备与候选计算、测速重叠，不能将它们相加作为总耗时。场景完成字段记录主循环第一次观察到任务结束的墙钟时间，可能略晚于线程实际完成。

2026-10-28 无窗口仿真记录 `runs/visualization/obb_early_vision.json`：初次观测 x=-1.261 m；首次合格测速帧 x=-1.197 m；冻结观测 x=-1.127 m；场景在速度合格前提交。冻结速度约 0.09678 m/s，对照仿真设定速度 0.1 m/s。首次帧到冻结帧约 1.434 仿真秒，工件移动约 0.134 m；早前对照 `obb_freeze_location_verified.json` 分别约 2.032 仿真秒和 0.207 m。不同运行的调度存在波动，不应当将这一次差值视为稳定性能保证。

完整规划在工件离开抓取区前仍未交付，结果为 `full_pick_window_expired_during_planning`，没有发送机械臂轨迹或验证抓取。宽视野第一帧的 OBB 可见点云也可能受到遮挡和视角影响，不能因为提前计算就认定抓姿准确。真实运行仍需要重新标定相机、检查分辨率及边缘深度、持续更新和场景认证，并针对规划瓶颈进一步优化。

## 抓取点诊断与路线预热

可视窗口中，绿色球表示当前提交规划请求的预测 TCP 接触位置，白色球表示从当前关节反馈计算的 TCP 位置。绿色球是请求目标，不表示已有认证轨迹。历史轨迹只有显式指定 `--replay-certified-overlay` 才会显示。输出 `requested_contact_targets` 分别保存基坐标、世界坐标、策略时间和仿真时间。`planner_result_target_diagnostics` 把失败后的修订目标明确标为未通过的提议；不能把它与原请求的接触时间配对。

例如 `obb_requested_contact.json` 中，提交与工作器有效请求均为世界坐标 `[-0.200, -0.0106, 0.5348] m`，接触时刻约为仿真 11.522 s。求解失败后工作器提出更长运动时间，修订后的接触时刻超出抓取区允许的窗口，失败结果因此包含区间外的提议位置；它不是原来的目标，更不是实际接触点。

`--warm-roadmap` 在仿真开始前预热现有静态关节空间路线图，给 `full_preplanned` 提供候选路线提示。预热独立计时，图不含本次工件的场景认证；每次查询仍须对当前工件、场景和完整轨迹重新认证。首次实验预热约 3.33 墙钟秒，图已就绪，但这次仍未交付认证轨迹，不能宣称已解决规划瓶颈。路线图与实际移动到等待位是不同功能：当前还没有经过认证、连续执行的提前移动到等待位并对接短抓取轨迹的链路。

## 中心线上方等待姿态实验

增加 `--standby-at-reset`：在 MuJoCo 重置时用 IK 将 TCP 设在世界坐标 `[0.04, 0, 0.70] m`，即抓取区中点和中心线上方 0.20 m，夹爪按配置的向下四元数设置。初始化后检查 2 mm 位置误差、0.012 rad 姿态误差、模型自碰撞和仿真静态场景状态。该模式是**仿真重置状态**，不是实际从旧姿态移动到等待位的经过认证轨迹；不适用于实机。现场仍需实际反馈起点、当前场景、时间参数化和完整连接认证。

执行仿真时，规划控制器的关节命令范围现在收紧到仿真执行器和规划器范围的交集，并将规划关节余量提高到不小于执行器的命令余量；硬限位不一致或当前反馈不在交集内则拒绝。发送时仍独立核对原有仿真执行器限幅，不把截断后的轨迹当作原认证轨迹。

运行示例：

```bash
PYTHONPATH=src/nero_core:src/nero_bringup MUJOCO_GL=egl OPENBLAS_NUM_THREADS=1 \
  python tools/probe_measured_network_scene.py --output runs/visualization/obb_standby_final.json \
  --early-vision --standby-at-reset --grasp-source obb --execute-sim --freeze-visual \
  --compute-budget-s 2.7 --seconds 30 --viewer --hold-viewer
```

在对齐执行器限制之前，一次实验从该初始化等待位得到认证抓取计划并发送 227 个仿真控制样本；执行器发现规划和实际命令限位不同而中止，未闭合、未抓取。对齐限制之后仍应看新的验证结果，不能把旧计划当成修复后的成功轨迹。

### 仿真限制对照（2026-10-29）

对中心等待位进行一次诊断：`--sim-condition-limit 70 --sim-tcp-linear-limit 0.30 --sim-tcp-angular-limit 1.0`。上述三个参数仅影响本仿真进程；并非厂家指标，也未验证实机适用性。关节命令仍取规划与仿真执行器范围交集，最小余量为 0.055 rad；碰撞检查和完整轨迹认证仍开启。本次关闭后续视觉和在线场景复核仅用于同一冻结视觉对照。

结果 `runs/visualization/obb_standby_adjusted_limits.json`：第一个候选启动规划，工件抓取窗口耗尽前没有收到规划结果；未认证轨迹，发送命令 0 条，第二候选未启动。因为工作器没有返回诊断，不能判断本次具体卡在奇异性、逆解、碰撞还是其他计算步骤，也不能声称调参改善或恶化了其中某一项。应增加运行中分阶段计时和可取消的单候选预算，再对不同候选及等待姿态测量；不要将参数直接用于实机。

`--sim-disable-tcp-and-singularity-limits` 是显式仿真诊断，关闭 full-preplanned 请求的雅可比条件数上限和 TCP 线、角速度上限。规划时的标称笛卡尔速度仍用于拦截时间估算；不表示这些数值仍是 TCP 速度上限。仿真执行器关节位置/速度/加速度、碰撞检查、抓取窗口与轨迹认证仍生效。此实验不支持真机；不得将其结果视为设备能力证明。

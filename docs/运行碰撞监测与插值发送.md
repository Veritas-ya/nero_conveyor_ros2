# 运行碰撞监测与插值发送

匹配版和固定位置单帧版的真机配置共用此功能。启动命令不变，重新启动抓取程序后使用新设置。程序不会自行使能、启动 CAN 或启动机械臂。

```yaml
runtime_sweep_mode: process_periodic
runtime_sweep_hz: 20.0
runtime_sweep_max_age_s: 0.2
pick_settings:
  control_hz: 100
```

离线规划仍先生成并检查整条轨迹，关节位置、速度和加速度限制及碰撞裕量不变。运行期间，发送端每10 ms按当前单调时钟求值这条连续多项式曲线，使用原曲线的插值与速度、加速度，不等后台逐点提供新目标，也不从旧指令向未知位置无限外推。到达轨迹末端后继续发送该末端，按原真实反馈到位规则交接；规划下一段时继续使用原静止守位逻辑。

运行扫掠改为独立进程中的周期监测。相机、SDK、CAN句柄、执行器和日志线程均不传入子进程。子进程重建私有运动学模型，安装主进程已过滤的场景、原工件点云和当前载物估计；不重新检测工件或修改标定。每次检查仍用三个时间切片和0.008 rad关节弦采样，保留原自碰撞、环境、带面、载物与释放点云检查，以及当前工件检查开关和取消后的工件接触恢复策略，不开启原来关闭的检查。

20 Hz是提交上限：最多一项正在计算、一份最新反馈请求，不积压全部历史请求。后台偶尔算慢时，发送端继续对已交付轨迹插值。主线程负责进程通信和结果接收，发送回调只发布小请求、读取已完成结果，不执行扫掠、进程序列化或等待计算完成。进程在打开设备前预热，每段运动开始前先完成一次真实反馈几何检查。

几何监测由监督线程独立读取非阻塞反馈；从开始等待预约时刻起就持续运行，不依赖发送回调已经开始。发送端发布完整的接触/载物阶段信息，监督线程用它配合最新实测关节和原包时戳更新检查请求。重复的旧反馈不重复提交，也不能延长结果有效期；两个反馈观察者分别记录自己的时钟高水位，避免并发读造成错误的时钟倒退判定。

反馈读取使用非阻塞快照。短暂没有新包时沿用最近一份实际反馈，保留原包时间戳；它不变成新反馈，不延长反馈有效期，也不能重复计入夹持确认时间。实际设备故障仍直接传播。发送前仍检查取消、身份、轨迹/场景版本、相机与设备时钟代次、反馈新鲜度、FK一致性、夹持状态、目标关节范围及发送速度约束。

200 ms上限从已完成几何检查所用的真实反馈时刻计时，包含排队和计算时间；结果到达时不能重新刷新年龄。后台检查拒绝、进程失效或结果过期后取消当前轨迹，进入原恢复处理，不能为了凑100 Hz继续发送失效轨迹。进程的迟到结果不能刷新另一任务、场景或已经关闭的运动段。

降低运行检查频率意味着不再逐发送周期扫掠每个中间反馈状态。它是周期监测，不能把一份检查结果称为对后续200 ms所有实际状态的连续碰撞证明。完整规划路径的几何检查仍保留；运行监测的发现延迟受20 Hz周期及计算耗时影响。

旧逻辑中，某次扫掠超时会触发取反馈重查，随后又按这次耗时预测准备提前量，可能进一步等待。新模式将准备时间预测限制在一个发送周期内，避免单次调度异常额外制造同样长的下一次等待。`inline`兼容模式保留原逐发送周期扫掠行为。

每段结束的 `dispatch_timing` 保存发送间隔和回调耗时；`runtime_sweep_timing`另保存后台提交/完成次数、实际完成频率、结果最大年龄、进程往返时间和工作进程PID。启动摘要和 `--check-config` 输出显示模式及两个频率。

这不是操作系统硬实时保证。SDK调用阻塞、主进程其他Python线程竞争和系统调度仍可能使实际发送间隔波动；需要复测时用实际发送时间和原时间戳反馈判断，不能把离线理想反馈试验称为真机成功。

2026-11-14的首次现场记录发现：旧版监测输入仅在发送回调更新。抓取预约等待约3.2秒、恢复预约等待约0.41秒时，后台不断重查最初那份反馈，导致正式发送前误报200 ms过期。已改为上面的独立反馈采样；200 ms上限、20/100 Hz设置及其他抓取策略不变。

当天17:13的记录进一步发现：监测已刷新，但发送器首次非阻塞读取暂时失败时，仍回退到等待开始时的私有缓存。现在监督线程会发布完整的、已验证的真实反馈快照；发送器读取暂时无数据时，可选用这份快照。只有姿态、关节和夹爪三组原始时间戳都不早于发送器缓存，才替换缓存，避免后台迟到读取覆盖新数据。发送器仍执行自己的新鲜度、时钟代次、FK和夹持检查，设备异常直接传播；重复缓存不延长200 ms有效期。`runtime_sweep_timing.sender_feedback_cache`记录缺样和使用后台反馈的次数，反馈过期错误记录具体包组、原始映射时间和年龄。

# 两秒真机入口的运行日志

`two_second_pick` 现在在启动模型、CAN、相机之前创建输出目录和 `events.jsonl`。原启动命令不变，每次仍须使用新的 `--output` 目录。默认检查配置不创建运行记录，也不连接设备。

## 终端只看当前步骤

2026-10-30 起，`--execute` 默认输出简短中文提示，启动命令无需修改。取消每3秒打印整份视觉诊断和结束时打印完整JSON；参数、哈希、拒绝原因统计、逐候选耗时等仍完整保存在文件中。省略 `--execute` 的配置检查继续输出机器可读JSON，便于现有检查工具使用。

提示依实际事件依次显示：启动/回位 → 检测与测速 → OBB抓姿候选 → 规划中 → 轨迹已得到 → 接近与跟随闭合 → 夹持反馈确认 → 抬升 → 搬运 → 张爪 → 返回。未交付轨迹时不会显示“已得到”；每个步骤只报关键变化，长时间等待约每10秒提示一行。瞬时视觉阶段切换经过消抖，不逐帧刷屏。

冻结速度显示沿标定传送带方向的卡尔曼速度（cm/s），不是固定取基座X分量。交付轨迹后显示实际选定抓姿的基座系XYZ固定轴RPY（度），以及预测接触时的TCP坐标（基座系毫米）；不会把曝光时的抓姿坐标当作未来接触点。

失败示意（仅展示格式）：

```text
[测速] 已冻结 4.70 cm/s（卡尔曼，11 帧/0.53 s）
[抓姿] OBB 已生成 4 个候选
[轨迹] 正在求解并检查抓取轨迹
[停止] 抓取轨迹规划：未找到可行抓取轨迹
[日志] /home/ubuntu22/nero_conveyor_ros2/runs/two_second_hardware/本次目录
```

成功走完程序时显示“反馈周期结束”，保留真实抬升/入框仍需现场证据的说明。Ctrl+C显示取消；独立 `move_to_wait --execute` 同样只显示连接、回位、完成或失败以及记录目录。

终端格式化由原日志后台线程处理，100 Hz发送线程仅记录事件入有界队列；终端卡顿或队列满不会阻塞发送。终端输出异常单独记录为 `journal.observer_errors`，不影响已保存的详细事件；极端卡顿可能与磁盘慢一样造成队列丢弃或写线程未及时结束，仍会在 `journal` 中报告。日志后台耗时 `writer_wall_s` 继续只统计文件写入，不把终端显示计入磁盘保存耗时。

接收到正常CAN反馈后先进入 `startup_readiness`，检查夹爪受力和张开宽度；机械臂不在等待位时使用共享脚本逻辑平滑回位，到位后恢复抓取发送模式，再开启相机。`startup_feedback` 保存初始依据，`startup_return_wait_*` 保存回位的跳过、发送、反馈、到位及失败记录，`summary.json.startup_return_wait` 保存完整结果。回位失败不会开启相机；不会自动开爪或使能。异常 `details` 列出实际值、配置值、差值及原容差。接纳目标后仍严格检查起始状态，不在此时自动回位；“OBB已生成候选”表示目标已就绪，实际规划提交以文件中的 `planning_submitted` 事件为准。相关历史实测问题见[19:14测试分析](真机抓取失败分析_20261029_191431.md)。

## 查看位置

每次运行的输出目录包含：

| 文件 | 记录内容 |
|---|---|
| `events.jsonl` | 启动阶段、每秒进度、合格目标、规划/执行关键事件、异常和退出；运行时即可读取 |
| `summary.json` | 退出状态、最后阶段、视觉阻塞原因统计、每类原因最近一次上下文、耗时、日志写入健康状态 |
| `cycle_001/events.json` | 进入任务后产生的原有事件；没有合格目标时不创建任务目录 |
| `cycle_001/execution_trace*` | 原有轨迹/发送/反馈证据，在控制线程退出后保存 |

例如，运行期间在另一个终端查看（将目录替换成此次命令的 `--output`）：

```bash
NERO_RUN_LOG_DIR=/home/ubuntu22/nero_conveyor_ros2/runs/two_second_hardware/本次目录
tail -f "$NERO_RUN_LOG_DIR/events.jsonl"
```

运行结束后，快速列出最后阶段和阻塞统计：

```bash
python3 - "$NERO_RUN_LOG_DIR/summary.json" <<'PY'
import json, sys
s = json.load(open(sys.argv[1]))
v = s.get('vision_diagnostics') or {}
print('退出:', s['status'], '信号:', s.get('received_signal'), '错误:', s.get('error'))
print('运行阶段:', s.get('last_runtime', {}).get('phase'))
print('规划器:', s.get('last_runtime', {}).get('planner'))
print('原因统计:', v.get('blocker_counts'))
print('最近未通过:', json.dumps(v.get('last_blocker'), ensure_ascii=False, indent=2))
print('写盘状态:', s.get('journal'), s.get('log_save_errors'))
PY
```

## 等待抓取时的具体原因

每个跳过观测的分支都计数。每秒快照之间短暂出现的原因，也保存在 `blocker_counts` 和 `last_blocker_by_reason`；后者按原因保留最近一次的帧、时间和数值。它们是诊断历史，不能把历史 `last_blocker` 当作当前仍未通过的条件；当前计算位置看 `stage`。

| 原因 | 含义与相关记录 |
|---|---|
| `feedback_missing` / `feedback_time_missing` | 无有效反馈或缺少可转换的反馈时间 |
| `feedback_frame_skew` | 反馈与曝光估计相差超过原有0.2秒条件；保存双方时间和差值 |
| `belt_surface_not_ready` | 带面未拟合成功，保存原拟合错误与原因 |
| `meter_not_current` / `no_tracks` | 测速器当前结果无效，或没有工件轨迹 |
| `no_qualified_tracks` | 轨迹未达到原测速条件；逐条保存确认状态、漏检、样本数、时间跨度、速度、波动及未通过原因 |
| `multiple_qualified_tracks` | 当前存在多个符合条件的目标，不能绑定唯一工件 |
| `too_far_upstream` | 工件仍在允许冻结距离之外；保存到入口距离及配置上限 |
| `already_at_entry` | 观测时已到达或越过抓取入口 |
| `insufficient_planning_time` | 预测入区前的剩余时间小于原规划预留；保存实际剩余时间及要求值 |
| `detection_*` | 工件数量、几何或轨迹关联未通过，保存检测原因和可用的候选数量/距离 |
| `observation_stale_before_detection` / `observation_stale_after_detection` | 观测在检测前/后超龄；保存实际年龄及原上限 |
| `vision_exception` | 视觉线程异常，保存发生异常的原阶段、异常类型和内容 |

`frame` 中保留帧序号、相机时钟代次、设备时间、主机接收时间、深度曝光时间估计与转换依据；不会将SDK软件时钟拟合写成硬件同步。目标观测位置、冻结预测速度与机械臂反馈仍各自记录。

规划期间的进度包含当前候选、IK路径点索引/总数、对应轨迹时间、候选已用时间和剩余预算；也标记场景准备、多项式检查、几何检查等阶段。已结束候选的结果与耗时保存在 `planner.completed_attempts`，最终异常仍保留原详细约束数值。

## 时间、开销与退出

- `monotonic_s` 是主机单调时间；UTC时间仅便于阅读。设备时间单独列出，不直接与主机时间相减。
- `vision.stage_wall_s` 是视觉线程的阶段占用；`operation_timings_s` 是操作耗时的次数、总计、均值、最近值和最大值。它们互有重叠，不可再次相加；视觉与规划并行时也不能把两者总计当作单件延迟。
- 高频控制只向内存和有界队列记录；后台线程每条写入后flush。每秒进度不保存图像、点云或大数组。原高频轨迹数组仍在发送结束后保存。
- `journal` 报告排队/落盘/丢弃条数、I/O错误及后台写入耗时。磁盘慢导致队列满时记录丢弃数量，不阻塞轨迹发送。`log_save_errors` 报告退出时轨迹/摘要保存失败。
- Ctrl+C（SIGINT）、SIGTERM、正常结束与捕获的异常都会收尾并保存摘要。SIGKILL、断电无法保证最终摘要；已flush的JSON行可辅助排查，但不承诺磁盘断电持久性。

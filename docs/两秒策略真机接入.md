# 两秒策略的真机代码接入

新入口为 `two_second_pick`，源码位于 `src/nero_core/nero_core/two_second/`。它运行本轮 OBB 两秒策略，与原 `full_preplanned` 入口独立。旧工程目录没有修改。已完成现场相机和机械臂状态接入，尚未完成实机抓取验收。启动、等待、规划和执行诊断现可持续保存，参见[日志查看与原因说明](两秒日志诊断.md)。

## 实际运行逻辑

1. 启动前加载现场相机外参、物理标定 TCP 或用户确认与实物一致的模型名义 TCP，以及工作区配置，准备运动学模型。连接 CAN 后先检查空爪和正常反馈；未在等待位时调用[共享回位逻辑](机械臂返回等待位.md)，以厂家 `move_j` 平滑回位并确认到位，恢复抓取配置模式后才开启相机。相机 SDK 只打开一次，视觉线程读取同一来源的原生 RGB-D 缓存。
2. 沿用原生深度、带面拟合、目标边缘补全、自体过滤和 Nero7 `legacy_depth → BlockTracker → XY KalmanMotion` 测速。达到有效测速条件且同一实测工件进入抓取入口上游 0.35 m 内、还未到达入口，并保留 1.5 s 规划时间后，用同曝光点云构建可见 OBB，生成短边/长边及翻转方向候选；此入口不调用 GraspGen-X。
3. 保存曝光设备时间、主机曝光估计、接收时间和时钟代次。冻结速度和 OBB，按 `曝光位置 + 速度 × (预测接触时刻 − 曝光时刻)` 预测。XY 速度是相机测量值，Z 运动沿用旧算法的实测带面切向模型。活动任务期间相机持续接收并监测时钟代次，暂停冗余测速和抓姿计算。返回成功后以新曝光和新卡尔曼历史恢复下一件，旧结果不改写本任务轨迹。
4. 仿真和真机共同调用 `reference.predict_entry_time`；仿真使用世界 X，真机使用 `s=dot(p_base,d)`。入区时刻基于测速器当前实测位置；OBB中心单独用于抓姿，二者不混用。入口上游超过 `freeze_upstream_distance_m` 时只继续跟踪；检测耗时若耗尽规划预留，不发布过期目标。接纳后预测进入抓取区的时刻，TCP 从现场配置且实际已到达的等待位，采用平滑接近曲线，优先两秒，必要时联合选择更长时长并重算未来接触点；闭合期间按冻结速度继续跟随。不能在提前发送开始前交付的轨迹被拒绝，不推迟后使用旧接触点。
5. 当前现场配置显式采用 `smooth`：共享五次接近/跟随/减速参考，高精度 DLS 及有界回退，检查整条七轴曲线的 q/v/a 多项式极值、加密采样的自碰撞/场景/带面间隙，以及 FK 对所选 TCP 参考的偏差。抓取时长候选为2、3、4、5.5、6.5秒，逐个重算拦截点并认证；全部失败则拒绝，不强制执行。

   为减少失败候选的交付开销，现先做预测范围、IK及q/v/a检查，通过后才构建本次曝光的场景并做几何认证；同一任务候选复用该场景，下一任务重新准备。平滑连接、候选可取消预算和完整时间参数化现已接入生产入口，详见[当前迁入与验证](平滑连接与时间参数化真机迁入_20261029.md)。
6. 发送由原 `JointStreamSender` 内部采样，调用原 `Hardware.move_joints → move_j/move_js`，保留通道独占、反馈时钟及故障停机。没有假设驱动支持 JointTrajectory、速度指令或硬件预约执行。
7. 到所选接触时刻发起闭合时，检查实际 TCP 对冻结目标预测的误差、方向、相对速度造成的闭合期间漂移和剩余跟随时间。随后同时发送跟随轨迹并读取宽度/受力；确认后继续执行1.5秒连续减速，到静止端点后再抬升。
8. 在夹持确认的反馈时刻，依据实际 TCP 和视觉预测点云固定载物相对变换；减速后不再按带速推进该点云。RRT-Connect 搜索绕行关节路线并对最终曲线按约束重新定时；后台规划期间持续保持上一条已认证曲线的静止终点，跨阶段保留发送历史，检查载物与场景及非手指部位的碰撞。搬运时继续读原夹持反馈，失去夹持则停止。到配置料框位检查张爪扫掠、张爪、按反馈返回等待位，再消费新目标。

`T_base_object_at_exposure`、`T_object_tcp_selected`、未来目标预测、实际 TCP/关节反馈分别保存。物体坐标系来自可见 OBB，不等于重建了被遮挡的真实外形。放置后返回时保留释放瞬间点云估计；它不是落料后的新视觉观测，不能证明料框内稳定放置。

## 沿用参数与现场必填项

命令参考现场当前提前 **80 ms**（2026-11-04按用户要求由100 ms调整），通过提前开始发送整条参考曲线实现，不跳到轨迹中间。当前机械臂参考和闭爪触发共用这个提前量；它是补偿参数，不是已经精确标定的硬件内部延迟。启动与候选计算按当前实测时间计时；接近和搬运分别记录。控制期间只向内存/有界日志队列记录，后台持续写入低频进度和关键事件；大数组在退出发送线程后保存。

沿用 `PickSettings` 的 100 Hz、100 mm 张开、2 N 闭合请求、0.2 N 夹持受力门槛、30 mm 现场抬升请求、夹持开口大于 3 mm 且小于 96 mm，以及原 `PickCycle` 的 **0.4 s 连续宽度/受力确认**。搬运使用原开口偏差 3 mm 和失力持续 0.25 s 判断。闭合空间条件取原 `BaselinePolicyConfig`：水平 22 mm、竖直 12 mm、方向 0.25 rad；相对速度以原 0.25 s 闭合稳定时间内是否仍位于这些范围判断，不另造独立速度阈值。这组组合用于新真机入口，尚未完成物理验证，不能把仿真四件投放当作这些条件的实机验证。

通用模板在 `src/nero_bringup/config/two_second.hardware.template.yaml`。已从旧项目整理[历史现场候选及来源](旧项目现场配置核对.md)，包含相机外参、方向和设备接口；需确认这些记录仍适用于当前现场。用户确认现有夹爪与旧模型一致，候选已接入旧项目名义 TCP 并以 SHA-256 绑定；根据用户要求，工作区和闭合跟随区间已按仿真换算填入，尚未完成现场测量；用户给出的工件高度上限为 0.12 m；用户提供的等待关节及料框投放位已填入；用户随后更新了等待位，料框实际位置尚未现场验证。通用模板保留3%请求；当前现场配置按用户要求改为100%请求。速度边界继承100%策略的每轴 **2 rad/s**；2026-10-30按用户给出的厂家数据，现场加速度边界显式设为每轴 **8 rad/s²**；抬升和载物转运按独立配置请求每轴 **2 rad/s²**，完整定时、认证和实际发送共用该请求，来源为先前成功物理仿真，尚待实机验收，来源记录为用户转述的厂家规格，未通过CAN独立确认。历史0.15覆盖和2默认值不再是当前现场加速度边界。整条平滑抓取、减速和后续路线仍必须通过完整检查。显式加速度请求不得超过有来源的厂家能力数组；程序不提高或关闭固件上限，不自动使能设备。当前变更和失败回归见[厂家加速度与规划交付修正](规划交付与厂家加速度修正_20261030.md)，此前默认值历史见[现场限值覆盖删除](现场限值覆盖删除_20261029.md)。

相机标定文件沿用原 `runtime.yaml` 中 `runtime.camera` 格式，必须明确 native depth optical → robot base 的 `camera_to_world_cv`、相机序列号、calibration_id 和原生深度/彩色分辨率。物理 TCP 文件格式：

```yaml
source: physical_measurement
calibration_id: null  # 填写真实标定标识
T_flange_tcp: null   # 4x4，法兰到实际任务TCP；米
T_canonical_tcp: null # 4x4，标准平行夹爪抓姿轴到实际任务TCP
```

矩阵中的旋转必须正交且右手。用户确认旧模型与现有夹爪一致后，可使用 `source: model_nominal` 的旧 TCP，并在现场配置中填写该文件的 `confirmed_nominal_tcp_sha256`；文件内容变更后确认失效。模型值仍记录为名义值，不标为实测标定。加载后会更新运动学任务点的位置和方向。

## 安装与运行

在与 ROS Humble Python 3.10 兼容的环境安装 `requirements-hardware.txt`。厂家的 pyAgxArm 源码随工程迁入；本机入口使用的 Python 环境已安装 `python-can` 和 `pyorbbecsdk2==2.1.2`，后者与旧项目所用版本相同，核心扩展与 SDK 库哈希一致。其他电脑需按现场相机/固件与 Python 版本单独安装兼容的 Orbbec 二进制 SDK。缺失 SDK 时不会替换为模拟设备。

```bash
cd /home/ubuntu22/nero_conveyor_ros2
python -m pip install -r requirements-hardware.txt
# 与本机旧环境同版；实际 wheel 需兼容目标平台和 Python
python -m pip install pyorbbecsdk2==2.1.2
source /opt/ros/humble/setup.bash
colcon build --packages-select nero_core nero_bringup
source install/setup.bash
ros2 run nero_core two_second_pick --config /absolute/path/site.yaml --check-config
```

不加 `--execute` 只读文件检查，不连接 CAN 或相机。模板未填会列出缺项，返回码 2。新 launch 也默认只检查：

```bash
ros2 launch nero_bringup two_second_hardware.launch.py config:=/absolute/path/site.yaml
```

现场明确执行入口如下，本次没有运行这些命令。程序要求现场已完成使能、空爪已张开并提供正常反馈；启动时不在等待位会自动平滑回位，失败则停止，成功后继续相机与抓取流程。程序自身不使能、不回零或重置真实关节，也不自动开爪：

```bash
ros2 run nero_core two_second_pick --config /absolute/path/site.yaml \
  --execute --count 1 --output /absolute/path/new_run
# 或 launch 显式 execute:=true count:=1
```

成功返回 `cycle_completed_from_feedback` 只表示宽度/受力/关节状态流程完成。`physical_grasp_success` 保持 unknown/null、`physical_bin_placement_verified` 为 false，直到另有实物抬升及入框观测。Ctrl+C 取消当前任务，先停止并退出发送线程，运动已开始时走原故障停机，不自动张爪。异常后不会恢复旧目标或旧轨迹。

## 工件点云碰撞后的恢复（2026-11-03）

当前现场 YAML 已设置 `recovery_allow_workpiece_contact: true`，用于用户指定的轻质3D打印工件。抓取期间的机器人与工件点云相交仍取消该次任务；恢复阶段允许接触这次已取消工件的移动点云、载物点云或释放估计，避免闭合的空夹爪因同一工件点云再次被拒绝而触发急停。该权限只在旧发送器和规划线程退出后进入，覆盖保持、回位及必要的载物入框流程，所有恢复线程退出后撤销；不会延续到下一件正常抓取。

空爪返回已配置等待位并张爪；确认带载则先抬升、送入已配置料框并释放，再回等待位。机械臂自碰、关节/工作区、实测带面、原环境障碍和载物与环境检查继续执行；设备故障、反馈无效、无法确认夹持或回位失败仍停止。Ctrl+C 保持取消并退出。通用模板默认 `false`，配置检查和运行日志记录当前策略。首次现场验证前需要重启程序加载新配置。

离线重放 `continuous_20261102_162740_61301/collisions/collision_0001.json` 复现右指命中95个工件点：恢复范围内允许从该姿态退回，完整回位曲线通过其余几何及运动约束检查；恢复范围外仍拒绝同样的点云相交。原始证据和重放结果见 `runs/diagnostics/workpiece_contact_recovery_20261103/recorded_replay.json`。该验证没有连接设备，也没有发送真实运动命令。

## 与仿真相同的两秒触发计算

抓取空间区间是配置值，不是自动由“两秒”算出的；本配置 `s ∈ [-0.20,0.28]` m。使用同一个共享函数，仿真 `s=x_world`，真机 `s=p_base·d_base`，d为配置的单位带向。仅在 `s_in-0.35 ≤ s_obs < s_in` 时允许冻结，且 `t_entry=t_exposure+(s_in-s_obs)/v_s` 必须不早于 `t_now+1.5` s，观测年龄上限沿用仿真的1 s。

当前平滑配置的接触时刻 `t_contact=t_entry+T`，T优先2秒，候选为2、3、4、5.5、6.5秒；TCP接触点 `p_contact=p_OBB_TCP_at_exposure+v*(t_contact-t_exposure)`；所以观测年龄和规划/等待都包含在内。当前平滑配置闭合时继续跟随0.8秒，确认夹持后连续减速1.5秒。0.35 m是空间门槛，低速时仍可能出现较长预测时间，不保证预测点可达。持续获取新实测观测后再冻结有机会减少旧估计带来的误差；在完全相同的匀速模型下，仅等待不会自动改变预测接触点。真机保留工作区、全段闭合跟随、关节q/v/a和场景检查；本次未放宽这些条件。

本轮修复此前真机遗漏的上游冻结门槛，并把规划预留判断移到场景准备前；后续实际交付截止仍不变，场景准备耗时计入预算，不把预约起点向后推迟。回归60项通过，构建通过；上次在入口上游约0.459 m冻结的保存观测如今被判为 `too_far_upstream` 并留在跟踪阶段。没有执行新的真机抓取。

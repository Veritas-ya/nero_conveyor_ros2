# 规划交付与候选等待：定位和离线验证

2026-10-28 针对已记录的两种情况检查无命令 MuJoCo 视觉诊断。此前一次完整规划在策略时间 3.24 s 才交付，原请求的执行起点为 2.19 s；故即使轨迹当时通过认证，也不能按原时刻发送。另一次第二候选创建后一直处于 WAITING，未来预测位姿超出了目标选择使用的抓取区间。原记录没有保留当时完整的选择门控，因此这个解释来自已保存的目标位置、速度及当前选择代码，不视为对当时所有状态的完整复盘。

## 修改

- 世界系传送带 X 方向及其原点一起转换到机器人基座系；抓取区间仍使用原世界 X 坐标上下界，不再将基座原点错误当作世界原点。
- 目标进入完整规划前，按同一个策略时钟比较窗口剩余时间与原配置给出的规划预留、发送前最短时间、最短接近时间及截止余量。即便这个必要条件通过，仍需实际计算并认证完整轨迹。必要条件不通过则记录 `candidate_window_insufficient`，不再停在无明确说明的 WAITING。
- 诊断入口支持 `--compute-budget-s`，用于按同一策略时钟域的实测数据配置规划预留。默认保持原配置的 2 秒；墙钟秒数不能直接当作仿真策略秒数。
- 已认证结果超过起点且尚未运动时，若窗口允许，诊断入口最多一次按该次请求测得的策略时钟耗时加既有发送准备时间建立新预留；关闭旧上下文、用新观测和独立模型提交全新完整规划及认证。过期轨迹不会被时间平移后直接发送。若窗口不够，明确停止。该重试仅用于不发送动作的诊断入口，不改变生产控制器或现有执行门控。

## 测试结果

默认预留的实际网络仿真中，第 15 号候选因接近段检查失败，规划工作约 8.82 墙钟秒。第二候选建立时，其窗口仅剩约 1.006 个策略秒，原配置给出的必要最短总时间为 3.24 秒，因此以 `candidate_window_insufficient` 明确停止，而不是等待到仿真超时。该诊断不是第二候选可行规划结果。

另一轮将预留设置为 3.24 策略秒（来自此前一次测得的策略时钟请求至结果耗时，仅做实验，不作为硬件配置）。目标开始时窗口余量约 6.70 秒，最短必要时间约 4.48 秒。候选进入完整规划，但约 7.14 墙钟秒后仍因 TCP 速度、IK 收敛和雅可比条件相关检查未产生完整认证轨迹。两次输入帧、调度和候选有差异，不能作为严格的速度或成功率对照。延长预留会让目标进一步移动，不能保证轨迹可达。

完整结果：[默认预留](evidence_timing_20261028/default_budget.json)、[3.24 秒实验](evidence_timing_20261028/budget_324.json)。视觉和规划回归 576 项通过；ROS Humble 三个包构建通过。本轮没有发送仿真机械臂命令，没有验证物理夹持或真实设备。

时间安排和等待诊断已改善，但真实网络到可执行完整轨迹仍未成功：规划耗时与剩余抓取区间不匹配。单次记录不能确定稳定的计算预算；后续需要压缩完整规划的关键路径，并验证候选并行或提前准备不会破坏场景、目标身份和轨迹证书，才能在规定窗口内完成闭环。

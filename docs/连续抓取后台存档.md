# 连续抓取后台存档

连续模式原来的顺序是“回位确认 → 同步压缩并保存本轮轨迹 → 接管下一件”。2026-11-14 17:24这轮测试中，两件目标在回位确认后还有约195 ms、319 ms发送余量，但上一轮存档分别占用约1.25 s、1.12 s，导致下一件原预约过期。

现在的顺序是“回位确认 → 提交本轮已结束的记录 → 接管下一件”。数组转换、反馈对齐诊断、NPZ压缩和JSON写盘由专用后台线程执行。一次导出复用同一份数组生成NPZ和摘要，避免重复计算。执行器的发送线程和生产记录的工作已经结束后才允许提交；后台持有该轮轨迹、事件和结果，不调用机械臂、夹爪或规划器。

后台容量为4轮，包含正在保存的一轮。入队不等待磁盘。容量耗尽时当前轮仍留在主线程，程序在已回位的交接位置停止接收下一件，设备退出后等待已入队记录保存，再同步保存未入队的一轮。写盘错误会记录在日志中，并阻止随后接管新的工件；不会假报归档成功。Ctrl+C退出时等待已入队记录保存，最后再关闭事件日志并生成summary。

每轮仍保存 `execution_trace.npz`、`execution_trace_summary.json`、`events.json`、`report.json`。事件 `cycle_trace_saved` 可能晚于下一轮开始，这是后台保存的正常顺序。按 `cycle_index` 关联记录，不能按文件写入时间推断机器人动作顺序。

最终summary中的 `attempt_archive` 包含容量、提交/成功/待写数量、峰值积压、提交耗时、后台写盘总耗时和错误。`archived_attempt_count`只计入成功保存的轮次。`cycle_trace_save_failed`及`log_save_errors`明确显示保存失败。

使用原来的 `--continuous` 启动命令即可，重新启动抓取进程后生效。这项改动移除了显式同步写盘等待，并不保证Linux/Python调度或下一件规划一定满足所有截止时间；原回位确认、起点检查、发送截止和运动限制仍然决定是否可以执行。
